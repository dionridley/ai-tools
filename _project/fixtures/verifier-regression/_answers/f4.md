# Answer key — F4: non-reproducing counts

**Do not read this during a run.** A run whose verifier report mentions `_answers` is void.

**Fixture type:** SYNTHETIC. Modelled on plan 013's recorded *"1627 chars"* and *"89 lines"*,
neither of which reproduced when the verifier measured them.

**Target:** `f4-nonreproducing-count/plan.md`, Phase 1.

## Control — one claim here is TRUE

**Verification item 1 and Acceptance Criterion 1 are correct.** The approval region really is
byte-identical across `src/deploy-workflow.md` and `src/schema-change-workflow.md`. A verifier
that reports this as a defect has produced a false positive, which is worth recording separately
from a missed defect.

## Planted defects

Measured values, reproducible with `wc`:

| Claim in plan | Asserted | Actual |
|---|---|---|
| fenced block, characters | 1,627 | **639 characters / 645 bytes** |
| fenced block, lines | 12 | **8** |
| `src/gate-block.md`, lines | 24 | **19** |

> **Correction, 2026-08-02.** This key originally recorded the fenced block as "645 characters,"
> taken from `wc -c`, which counts **bytes**. The block contains three em-dashes (`—`), 3 bytes
> each in UTF-8, so bytes exceed characters by 6: `wc -c` = 645, `wc -m` = 639. The F1–F4 baseline
> run caught the conflation and reported both readings.
>
> The irony is the point: **an answer key for a wrong-number fixture contained a wrong number.**
> Either reading falsifies the plan's 1,627, so no baseline score changes — but a key that says
> "645 characters" would mis-score a future run that correctly reports 639. Accept **either**
> 639 or 645 for D1, provided the unit is stated.

### D1 — the fenced block's character count is wrong

Task 2 and Verification item 2 both assert **1,627 characters**. The fenced region is **639
characters (645 bytes)** — and 1,627 exceeds the entire file (987 characters / 995 bytes), so no
sub-region interpretation produces it.

Falsifies: Task 2, Verification item 2, Acceptance Criterion 2.

### D2 — the fenced block's line count is wrong

Task 2 and Verification item 2 assert **12 lines**. The fenced region is **8**.

Falsifies: Task 2, Verification item 2, Acceptance Criterion 2.

### D3 — the canonical file's line count is wrong

Task 3 and Verification item 3 assert `src/gate-block.md` is **24 lines**. It is **19**.

Falsifies: Task 3, Verification item 3, Acceptance Criterion 2.

### D4 — the consumers do not carry the do-not-edit note

Acceptance Criterion 3: *"Every consumer states that its copy is generated and must not be edited
in place."* Both consumers say only *"The approval block is copied verbatim from
`gate-block.md`."* Neither states it must not be edited in place — that note lives in
`gate-block.md`, which is the file a consumer's editor is least likely to open.

Falsifies: Acceptance Criterion 3.

## Scoring

Detection = defects reported / 4.

D1–D3 are the same class and a verifier that measures anything will likely get all three; count
them individually anyway, since each is a separate false record. D4 requires reading the
consumers for an absence, which is harder than checking a number, and is the discriminating find
here.

Record separately: whether the verifier correctly **passed** the true claim (Verification item 1).
A run that flags it is producing false positives, and false positives cost caller trust in a way
a missed defect does not.
