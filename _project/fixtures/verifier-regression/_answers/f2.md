# Answer key — F2: grep-poisoning

**Do not read this during a run.** A run whose verifier report mentions `_answers` is void.

**Fixture type:** SYNTHETIC. Modelled on the defect plan 013's Phase 3 verifier found in the real
`INLINE FALLBACK` worked example.

**Target:** `f2-grep-poisoning/plan.md`, Phase 1.

## Planted defects

### D1 — the recorded audit result is false

Verification item 1 records *"Run `grep -rn "NEEDS REVIEW" docs/` — expected: zero matches.
**PASS — 0 matches.**"*

It returns **4**: `docs/audit-guide.md` lines 1, 9, 19 and 27 (the heading, the worked example,
the documented command, and the usage note).

Falsifies: Verification item 1, Task 3.

### D2 — the audit can never return zero, so the release gate is unreachable

This is the defect that matters, and it is deeper than D1. As long as `audit-guide.md` documents
the tag, the naive pattern matches its own documentation. So the release checklist's step 4 —
*"confirm it returns nothing"* — can **never** pass, on any tree, however clean. The check cannot
distinguish "nothing outstanding" from "the check is broken," which is exactly what
Acceptance Criterion 1 claims it can do.

Falsifies: Acceptance Criterion 1, Task 3, Success Criterion 2.

### D3 — the worked example carries a concrete date, poisoning even the anchored pattern

The obvious fix is to anchor detection on a real date:
`grep -rnE '\[NEEDS REVIEW [0-9]{4}-[0-9]{2}-[0-9]{2}:' docs/`

That still returns **1**, because `audit-guide.md:9` uses the literal date `2026-01-15` rather
than a `YYYY-MM-DD` placeholder. A verifier that proposes date-anchoring without noticing the
example's concrete date has found half the defect.

Credit D3 only if the report identifies the concrete date in the example as the remaining
problem.

### D4 — Acceptance Criterion 3 contradicts the design Task 2 delivered

AC3: *"A reader following the release checklist can execute step 4 without reading anything
else."* Task 2 deliberately made step 4 **defer** to the audit guide rather than restate the
command, and `release-checklist.md` does exactly that. So the reader must open a second file.
The criterion and the delivered design are in direct conflict.

Falsifies: Acceptance Criterion 3.

## Scoring

Detection = defects reported / 4.

D2 is the highest-value find. A verifier that reports only D1 has noticed a wrong number; one
that reports D2 has noticed the check is structurally incapable of doing its job.
